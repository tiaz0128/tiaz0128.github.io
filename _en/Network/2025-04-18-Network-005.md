## HTTP Is Stateless

The HTTP protocol is **stateless** by design. Each request is independent, and the server doesn't remember anything about previous requests. That caused problems like these:

- After a user logs in, the login isn't kept when they move to the next page
- Items added to a shopping cart vanish when you move between pages
- User preferences can't be saved

Cookies are the key mechanism that lets you keep state on top of this stateless protocol.

## Cookies

A cookie is **a small piece of text data that a web server stores in the user's browser**{:.orange}. This data plays an important role in keeping state information between the server and the client.

### Where the Name "Cookie" Comes From

In 1994, Lou Montulli, a programmer at Netscape Communications, needed a mechanism to store and keep information between web browsers and servers, and he introduced the concept of cookies for the first time.

The name "cookie" comes from the resemblance to a fortune cookie: just as a fortune cookie holds a message inside, a cookie is a small piece of data that carries information.

![Lou Montulli](/assets/img/content/Network/005/002.webp){:.img-s}

`> Lou Montull – the inventor of the browser cookie`{:.img-caption}

### What Cookies Do

Cookies are small amounts of data that websites use to remember user activity, stored in the user's browser. Their main jobs are:

- Keeping users logged in
- Saving user preferences (language, theme, etc.)
- Keeping shopping cart contents
- Tracking and analyzing user behavior

## How Cookies Work

Cookies work like this:

1. The server sets a cookie through the `Set-Cookie` field of the HTTP response header.
2. The browser stores the cookie.
3. From then on, every time it sends a request to the same server, the browser includes the value in the `Cookie` field of the HTTP request header.

### Example Server Response Header

```http
HTTP/1.1 200 OK
Set-Cookie: user_id=12345; Max-Age=3600; Path=/
```

### Example Client Request Header

```http
GET /profile HTTP/1.1
Host: example.com
Cookie: user_id=12345
```

## Hands-On Example

{% include template/alert.html
  type="note"
  about="I used Python 3.13."
%}

Here we'll inspect and test cookies with FastAPI and the browser's Dev Tools. First, install the packages you need with the command below.

### Installing Packages

```bash
$ pip install fastapi "uvicorn[standard]"
```

### Source Code

FastAPI sets cookies with the `Response.set_cookie()` method, which lets you configure the various cookie options.

<div class="file-name">main.py</div>

```python
from datetime import datetime, UTC
from fastapi import FastAPI, Response, Request
from fastapi.responses import HTMLResponse

app = FastAPI()

# endpoint that sets the cookie
@app.get("/set_cookie")
async def set_cookie(response: Response):
    response.set_cookie(
        key="user_id",
        value="tiaz",
    )
    return {"message": "Cookie has been set!"}

# endpoint that reads the cookie
@app.get("/get_cookie")
async def get_cookie(request: Request):
    user_id = request.cookies.get("user_id", "none")  # read the cookie
    theme = request.cookies.get("theme", "none")
    return {"user_id": user_id, "theme": theme}

# HTML page for testing
@app.get("/", response_class=HTMLResponse)
async def home():
    return """
    <html>
        <body>
            <h1>FastAPI Cookie Test</h1>
            <a href="/set_cookie">Set cookie</a><br>
            <a href="/get_cookie">Check cookie</a>
        </body>
    </html>
    """
```

## Key Cookie Settings

{% include template/alert.html
  type="warning"
  about='When testing cookie attributes, always delete the existing cookie before each test!'
%}

The key cookie settings are:

- Cookie name and value (key-value)
- Expiration and lifetime (Expires, Max-Age)
- Domain and path restrictions (Domain, Path)
- **Security attributes (Secure, HttpOnly, SameSite)**{:.orange}

### key-value (required)

- The cookie's name (string)
- The value stored in the cookie (string)

```python
response.set_cookie(
    key="user_id",
    value="tiaz",
)
```

### max_age

- How long the cookie is valid (in seconds, integer)
- Without a value, the cookie is deleted when the browser session ends (session cookie)

```python
response.set_cookie(
    key="user_id",
    value="tiaz",
    max_age=30,
)
```

### expires

- The exact date/time the cookie expires
- When used together with max_age, max_age takes precedence

```python
response.set_cookie(
    key="user_id",
    value="tiaz",
    expires=datetime(2025, 12, 31, tzinfo=UTC),
)
```

### Session Cookies

A **persistent cookie** is one that has an Expires or Max-Age attribute and lasts for a set amount of time. Conversely, a cookie without Expires or Max-Age is called a **'session cookie'**.

| Property | Session cookie | Persistent cookie |
|------|----------|-------------|
| Lifetime | For the browser session | For the configured period |
| Stored in | Mostly memory | Disk |
| Deleted when | The browser closes | It expires or is deleted manually |
| Attributes | No Expires/Max-Age | Expires or Max-Age set |
| Security | Relatively safe | Potential for misuse |

### path

- The URL path where the cookie is valid
- Default: "/" (usable on every path)
- Example)
  - path="/get_cookie" (the cookie is used only on that path)
  - On path="/", the cookie isn't set in the Request header

```python
response.set_cookie(
    key="user_id",
    value="tiaz",
    path="/get_cookie",  # path where the cookie is valid
)
```

### domain

- A domain restriction: specifies the domains the cookie can be sent to
- "Only include this cookie when the browser sends a request to this domain"
- Default: the current hostname of the server setting the cookie (excluding subdomains) → "127.0.0.1"
- Example)
  - With domain="localhost"
  - When you visit "localhost" in the browser, the cookie is stored
  - When you visit "127.0.0.1" in the browser, the cookie is not stored (treated as a different domain)
  - **This happens because of the browser's security policy restricting cookie sharing across domains**

```python
response.set_cookie(
    key="user_id",
    value="tiaz",
    domain="localhost", # the browser stores the cookie only when visiting localhost
)
```

## Cookie Security Settings

Cookie security settings are especially important. Even in real-world projects, people frequently make mistakes when setting and using these attributes. Let's understand exactly what each attribute means and how it behaves, and try them out.

### secure

- When set to True, the cookie is sent only over HTTPS connections
- A must in production environments for stronger security

```python
response.set_cookie(
    key="user_id",
    value="tiaz",
    secure=True
)
```

{% include template/alert.html
  type="tip"
  about='You can test the `Secure` attribute by setting up a local domain. Check out <a class="none" target="_blank" href="/Network/4">`How DNS Works - The hosts File: Hands-On with Local DNS`</a>!'
%}

- Local development exception: for convenience during development, most browsers (Chrome, Firefox, Edge, etc.) allow cookies with the Secure attribute on `localhost` and `127.0.0.1` even without HTTPS.

- Production: on real internet domains, a cookie with `Secure=True` won't be set unless you use HTTPS.

### httponly

- When set to True, JavaScript can't access the cookie
- Prevents XSS (_Cross-site scripting_) attacks

```python
response.set_cookie(
    key="user_id",
    value="tiaz",
    httponly=False
)
```

With `httponly=False`, you can access and even change the cookie value from the browser console. When it's True, you can't.

```js
document.cookie = 'user_id=test1234'
```

### samesite

This setting controls whether the browser sends the cookie along with requests made from other sites.

- Values
  - "strict": send the cookie only on same-domain requests
  - "lax": allow some cross-site requests (e.g. clicking a link)
  - "none": send the cookie on every request (**requires secure=True**{:.orange})
- A setting for preventing CSRF attacks

```python
response.set_cookie(
    key="user_id",
    value="tiaz",
    samesite="strict",
)
```

| SameSite value | Same-site request | Link click | Form submit | iframe/image | fetch/XHR | Notes |
|------------|--------------|---------|--------|--------------|-----------|------|
| **Strict** | ✅ Allowed | ❌ Blocked | ❌ Blocked | ❌ Blocked | ❌ Blocked | Safest, but hurts user experience |
| **Lax**<br>(default) | ✅ Allowed | ✅ Allowed<br>(GET only) | ❌ Blocked | ❌ Blocked | ❌ Blocked | Balances security and usability |
| **None** | ✅ Allowed | ✅ Allowed | ✅ Allowed | ✅ Allowed | ✅ Allowed | Legacy behavior<br>(Secure=True required) |
