## HTTP and HTTPS

### HTTP

HTTP is the basic protocol for transferring data on the web. It sends data as unencrypted plain text, which makes it insecure.

### HTTPS (HTTP Secure)

HTTPS is the secure version of HTTP, built by combining the HTTP protocol with the SSL/TLS protocol. It uses SSL/TLS certificates to vouch for a website's authenticity. Because data is encrypted in transit, it is far more secure and protects your data from man-in-the-middle attacks, eavesdropping and the like.

## SSL (Secure Sockets Layer) and Certificates

Let's look at the SSL certificate you need for HTTPS communication.

### SSL (Secure Sockets Layer)

SSL is a protocol that encrypts web traffic and keeps it secure. It was originally created by Netscape, and the standardized version that followed is called TLS (Transport Layer Security). Still, most people keep using the term SSL.

### Certificates

A certificate is the core of SSL/TLS communication. You get verified by a trusted Certificate Authority (CA), which then issues you a certificate. The issued certificate contains important information such as:

1. Service information
   - Domain name
   - Organization name
   - Location, etc.
2. The server's public key
   - The public key itself
   - The encryption algorithm used (e.g. RSA, ECC)

### Types of Certificates

Certificates come in types based on how thoroughly they are vetted, and each type goes through a different level of trust and validation.

| Type | Meaning | Validation level | Issuance time | Trust | Typical use |
|------|------|-----------|-----------|---------|-----------|
| DV (Domain Validation) | Verifies domain ownership | Low | Fast (minutes to hours) | Low | Personal blogs, small websites |
| OV (Organization Validation) | Verifies the organization | Medium | Moderate (1-3 days) | Medium | Corporate websites, online services |
| EV (Extended Validation) | Extended validation | High | Slow (1-2 weeks) | High | Financial institutions, large enterprises, government agencies |

## Self-Signed SSL Certificate

First, let's create a self-signed SSL certificate and apply it to NGINX.

### 1. Create the SSL Certificate

Start by generating a self-signed SSL certificate with OpenSSL. Create a folder and run the command below. It generates a 2048-bit RSA key pair and a self-signed certificate valid for one year. When you run it, you'll be prompted to enter the certificate details.

```bash
$ sudo mkdir /etc/nignx/ssl

$ sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout /etc/nginx/ssl/self.key -out /etc/nginx/ssl/self.crt
```

- `req` : the command for creating certificate signing requests (CSRs) and certificates
- `-x509` : creates a self-signed certificate with no signature from a public CA
- `-nodes` : short for 'no DES'; the private key is not encrypted
- `-days 365` : sets the certificate's validity period to 365 days (one year)
- `-newkey rsa:2048` : generates a new 2048-bit RSA key pair
- `-keyout /etc/nginx/ssl/self.key` : the path where the generated private key is saved
- `-out /etc/nginx/ssl/self.crt` : the path where the generated certificate is saved

### 2. Edit the NGINX Configuration File

Next, change the NGINX configuration to use SSL. Create a new config file in the /etc/nginx/conf.d/ directory or edit an existing one.

```bash
$ sudo vim /etc/nginx/conf.d/default.conf
```

Point the `ssl_certificate` directive at the self.crt file, and the `ssl_certificate_key` directive at the self.key private key file.

<div class="file-name">/etc/nginx/conf.d/default.conf</div>

```nginx
server {
    listen 443 ssl;
    server_name ec2-3-36-45-120.....; # change to your own domain

    ssl_certificate /etc/nginx/ssl/self.crt;     # certificate file
    ssl_certificate_key /etc/nginx/ssl/self.key; # private key file

    # SSL settings
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers on;
    ssl_ciphers ECDHE-RSA-AES256-GCM-SHA512:DHE-RSA-AES256-GCM-SHA512:ECDHE-RSA-AES256-GCM-SHA384:DHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-SHA384;

    # the rest of the server settings
    location / {
        root   /usr/share/nginx/html;
        index  index.html index.htm;
    }
}

# redirect HTTP to HTTPS
server {
    listen 80;
    server_name ec2-3-36-45-120.....; # change to your own domain

    # redirect every request to HTTPS
    location / {
        return 301 https://$server_name$request_uri;
    }
}
```

### 3. Check the NGINX Configuration & Restart

After editing the config file, check it for syntax errors. If the configuration is valid, restart NGINX to apply the changes.

```bash
$ sudo nginx -t

$ sudo systemctl restart nginx
```

If you're on AWS, update the inbound rules of your Security Groups for `http` and `https` as needed.

### Check in the Browser

The self-signed SSL certificate is now applied to NGINX. When you visit the site in a browser, you can see that a secure connection has been established. A certificate like this is fine for development or internal testing, but you can't use it on a public production website, because it may show users a security warning.

## Recap: Issuing a CA Certificate

That's the whole process of getting a CA certificate issued. Let's look at the diagram again and make sense of the steps.

### Issuing a Certificate via a CSR

Let's recall the order of what we did on the GOGETSSL site.

1. Generate a CSR
2. Save the private key on the server
3. The CA validates the server
4. The server's certificate is issued

The CA digitally signs the server's certificate with its own private key.

### The Certificate in the Browser

Thanks to the digital signature the CA put on the certificate, the browser can use the CA's public key to verify that the certificate is valid.

A valid certificate contains the following:

- The server's public key
- The server's information
- The CA's digital signature

With the process above, we understand how the certificate proves the server's public key is safe. But how do we know the certificate itself is valid?

## How the Fullchain Works

Let's look at the `Fullchain` approach used to verify that a certificate is valid.

- The CA at each level signs the certificate below it with its own private key.
- Each certificate is signed by the CA directly above it.
- The root CA's certificate is self-signed.
- This repeats all the way up to the root CA, forming a chain of trust.
- The root CA's certificate is usually preinstalled in browsers and operating systems, acting as the anchor point of trust.

sequenceDiagram
    participant WS as Web server
    participant LCA as Issuing CA
    participant ICA as Intermediate CA
    participant RCA as Root CA

    WS->>LCA: 1. Submit CSR
    LCA->>LCA: 2. Create and sign server certificate
    LCA->>ICA: 3. Request issuing CA certificate
    ICA->>ICA: 4. Create and sign issuing CA certificate
    ICA->>RCA: 5. Request intermediate CA certificate
    RCA->>RCA: 6. Create and sign intermediate CA certificate
    RCA-->>ICA: 7. Signed intermediate CA certificate
    ICA-->>LCA: 8. Signed issuing CA certificate
    LCA-->>WS: 9. Signed server certificate + certificate chain
</pre>

The client (browser) follows this chain, verifying each certificate, until it finally reaches the root CA and confirms that the whole chain can be trusted.

## Creating the fullchain.crt File

The server setup isn't done yet, so let's keep going. A fullchain file combines the several certificates that make up an SSL certificate chain into a single file. You create it by simply concatenating the certificate files into one.

```bash
$ cat (server.crt) (Intermediate.crt) [Root.crt] > fullchain.crt

$ cat ec2-3-...compute_amazonaws_com.crt GoGetSSL_RSA_DV_CA.crt USERTrust_RSA_Certification_Authority.crt > /etc/nginx/ssl/GoGetSSL_fullchain.crt
```

### The Usual Order When Building a Fullchain File

The root certificate can be left out, since most browsers and operating systems already include it as a trusted certificate.

1. Server (domain) certificate
2. Intermediate certificate
3. Root certificate (optional)

## NGINX Configuration

To use this fullchain file in NGINX, just point the `ssl_certificate` directive at it. The private key file goes separately in the `ssl_certificate_key` directive.

<div class="file-name">/etc/nginx/conf.d/default.conf</div>

```nginx
server {
    listen 443 ssl;
    server_name ec2-3-36-45-120.....;

    ssl_certificate /etc/nginx/ssl/GoGetSSL_fullchain.crt; # chain file
    ssl_certificate_key /etc/nginx/ssl/GoGetSSL_private.key; # private key

    ...
}
```
