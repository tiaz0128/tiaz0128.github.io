## Setting Up the Environment

Starting with this post, let's take a close look at **Celery's key concepts and how to use them**!

### docker-compose

We'll use docker compose to run Redis and RabbitMQ. Write a `docker-compose.yaml` file and start the containers with the command below.

```bash
$ docker compose up -d
```

<div class="file-name">docker-compose.yaml</div>

```yaml
services:
  rabbitmq:
    image: rabbitmq:4.0-management
    ports:
      - "5672:5672"
      - "15672:15672"
  redis:
    image: redis:alpine
    ports:
      - "6379:6379"
```

## Celery Application

This is Celery's most fundamental instance, called the Celery Application, or simply the app. You create it with the `Celery` class.

### Folder Structure

```text
├── docker-compose.yaml
└── src
    └── run.py (new file)
```

### Writing run.py

<div class="file-name">src/run.py</div>

```python
from celery import Celery

app = Celery(
    "Celery App",
    broker="pyamqp://guest:guest@localhost//",
    broker_connection_retry_on_startup=True, # optional; without it you get a compatibility warning
)
```

- The first argument is the name of the instance being created, i.e. the Application.
- `broker` : the message queue
- `broker_connection_retry_on_startup` : whether to retry when the connection to the broker fails at startup

### Running Celery

The command below **starts a Worker**{:.orange} that takes tasks (Tasks) from the broker and processes them.

- `-A run` : the package containing the app object
- `worker` : run a Celery Worker

First, let's look at the output.

```bash
$ cd src

$ celery -A run worker
```

## Celery Tasks

A Task is the basic building block of a Celery Application. A Task plays two roles:

- Sending messages
- Defining what happens when a Worker receives that message

So let's see how to define a Task.

### Folder Structure

Create a `tasks` folder and write a `math.py` file.

```text
├── docker-compose.yaml
└── src
    └── run.py 
    └── tasks
        └── math.py (new file)
```

### Writing math.py

<div class="file-name">src/tasks/math.py</div>

```python
from run import app

@app.task
def add(x, y):
    return x + y
```

### The Celery.task Decorator

The `Celery.task` decorator lets you define a Task; here `@app.task` does that job. It **turns the plain callable function `add` into a Task object**{:.orange}.

In fact, the decorator does the same thing as:

```python
app.task(add)
```

```bash
$ cd src

$ celery -A run worker
```

But if you run Celery again, you'll see that `[tasks]` still shows no registered Tasks.

## Task Registry

A Celery Application keeps a `tasks` dictionary internally, called the Task Registry. To use a Task object you've created, it has to be registered in this dictionary. The Task's name is the key and the Task object is the value.

### Updating run.py

Add code to `src/run.py` that registers the Task. The `register_task` method registers a Task object in the Task Registry. Run Celery again and you'll see that our `add` Task is registered.

<div class="file-name">src/run.py</div>

```python
from celery import Celery

app = Celery("Celery App", broker="pyamqp://guest:guest@localhost//")

from tasks.math import add

app.register_task(add)
```

```text
(omitted)

--- ***** ----- 
 -------------- [queues]
                .> celery           exchange=celery(direct) key=celery

[tasks]
  . tasks.math.add
```

### Task Names

Every Task has a unique name, and the Celery Worker uses that name to find the function to run. By default, Task names are generated automatically in the form **[package].[module].[function]**{:.orange}.

You can change it to whatever you like with the `name` option of the `Celery.task` decorator.

```python
@app.task(name="add_task")
```

## Improving the Code

The code so far doesn't read very well. Let's improve it using some of Celery's features.

### shared_task

With `shared_task`, you don't need to reference the Celery app instance directly.

<div class="file-name">src/tasks/math.py</div>

```python
from celery import shared_task

@shared_task
def add(x, y):
    return x + y
```

- Task code can be reused across multiple Celery apps
- Handy when developing reusable libraries or packages
- Avoids circular import problems

### The include Option

With Celery's `include` argument, Tasks in the listed modules are registered automatically when the Celery Worker starts. When you add a new Task, just add its module path.

<div class="file-name">src/run.py</div>

```python
from celery import Celery

app = Celery(
    "Celery App",
    broker="pyamqp://guest:guest@localhost//",
    include=["tasks.math"],
)
```

## Putting a Task in the Queue

  type="caution"

### Celery cli : call

Let's put a Task in the queue using the **Celery CLI (Command-Line Interface)**. The command below calls a Task by its name. Calling a task **puts it into the queue as a message.**{:.orange}

```bash
$ celery call -a '[1,2]' --eta '2025-02-14T13:00:00+09:00' --countdown 10 tasks.math.add
```

- `-a '[1,2]'` : passes the Task's arguments as a JSON array
- `--eta '2025-02-14T13:00:00+09:00'` : eta (Estimated Time of Arrival), the scheduled start time
- `--countdown 10` : wait 10 seconds before running
- `tasks.math.add` : the name of the Task to run

### Checking the RabbitMQ Queue

Let's check in RabbitMQ that the Task arrived in the queue as a message. In the RabbitMQ web console, open the `Queues and Streams`{:.path} tab and look at the `celery`{:.path} queue: there's a message in the `Ready` state.

```text
http://localhost:15672/

guest / guest
```

## Task Workflow

Now let's watch the process of fetching the queued message and running the Task. Start the Celery Worker.

```bash
$ cd src

$ celery -A run worker
```

### 1. Task received

As soon as the Celery Worker starts, it **receives the message**{:.orange} from the queue. The task isn't run yet; it waits until the `eta` time.

```text
[2025-02-14 13:09:34,765: INFO/MainProcess] Connected to amqp://guest:**@127.0.0.1:5672//
[2025-02-14 13:09:34,772: INFO/MainProcess] mingle: searching for neighbors
[2025-02-14 13:09:35,811: INFO/MainProcess] mingle: all alone
[2025-02-14 13:09:35,827: INFO/MainProcess] celery@DESKTOP-HRVSRM8 ready.
[2025-02-14 13:09:35,829: INFO/MainProcess] Task tasks.math.add[609974ca-4b9c-4544-88ba-3bf51cd0c8c1] received
```

### 2. Message Unacked

In RabbitMQ you can see the Celery Worker connected as a consumer, and the message has changed from `Ready` to the `Unacked`{:.orange} **state**{:.orange}. A message **is not removed from the queue until the Celery Worker acknowledges it.**

![Consumer](/assets/img/content/Celery/002/004.webp)

![Unacked](/assets/img/content/Celery/002/003.webp)

`> The message state changed from Ready to Unacked`{:.img-caption}

### 3. Acknowledge

By default, the Celery Worker **acknowledges the message**{:.orange} right before running the Task. So when the Task runs after `--countdown 10`, the message is deleted from the queue.

```text
[2025-02-14 13:10:00,003: INFO/ForkPoolWorker-2] Task tasks.math.add[609974ca-4b9c-4544-88ba-3bf51cd0c8c1] succeeded in 0.000499843001307454s: 3
```

![acknowledge](/assets/img/content/Celery/002/005.webp)

`> The Unacked message is deleted as the Task runs`{:.img-caption}

## Wrapping Up

This time we looked at Celery's most fundamental building blocks. 😊

### Celery Application

- The instance that serves as Celery's starting point
- Manages the basic setup, such as the broker connection and Worker settings
- Manages Tasks through the Task Registry

### Celery Tasks

- Defining Tasks with the `@app.task` decorator
- Better reusability with `shared_task`

### Task Execution Flow

- Task published → stored in the message queue → received by a Worker → Task runs
- Message state changes: Ready → Unacked → Acknowledged
