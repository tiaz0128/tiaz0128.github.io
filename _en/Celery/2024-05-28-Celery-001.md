## The Response Is Too Slow

If handling a request (_Request_) takes a long time, the screen has to sit and wait until the response (_Response_) arrives.

![Wait Response](/assets/img/content/Celery/001/001.webp)

`>Still no response... should I hit refresh or not?`{:.img-caption}

So instead, we put the request's work into a queue, send the response first, and do the actual processing in the background. This approach is called *distributed processing with a 'Task Queue'*{:.yellow}**.**{:.yellow}

A task queue is a system that pulls long-running or resource-heavy work out of the main application flow so it can be processed in the background.

## Celery

![Celery logo](/assets/img/title/Celery/Celery.webp){:.img-200x200}

In Python, `Celery` is the go-to tool for task queues. It's mostly used to handle background jobs in web applications, and it's very handy for building distributed systems.

Celery is made up of three main components.

- Client
- Broker
- Worker

## Celery Components

### Client

The client creates tasks and sends them to the broker; it's also called the `Producer`. Usually a web application or a script plays the client. It uses Celery to define tasks and request their execution.

### Broker

The broker relays messages between the client and the workers, and is also called the `Task Queue / Message Queue`. It stores task messages and hands them to workers.

### Worker

A worker is the process that takes tasks from the broker and actually runs them; it's also called the `Consumer`. You can run several workers at once to process tasks in parallel. Workers can store task results in the result backend.

    url="https://www.youtube.com/embed/0lyrd5FlETQ?si=pgezWMadC3_G_1_9"
%}

`> Yalpakhan Coding Dictionary: Message Broker - Kafka and RabbitMQ explained`{:.img-caption}

## Additional Components

These components are optional.

### Result Backend

Stores task states and results. The client uses it to look up a task's status or fetch its result. Redis, a database, and so on can serve as the backend.

### Others

- `Beat`: a scheduler for periodic tasks
- `Flower`: a web-based tool for monitoring and managing Celery

## How Celery Works

![Celery working flow](/assets/img/content/Celery/001/002.webp)

1. The client creates a task and sends it to the broker
2. The broker stores the task in a queue
3. The worker watches the broker's queue and picks up new tasks as they arrive
4. The worker runs the task
5. The task result is stored in the result backend (if configured)
6. The client queries the result backend for the task's status or result as needed

## Writing the FastAPI App

### Installing Libraries

First, let's install the Python libraries we need.

```bash
$ pip install Celery fastapi

$ pip install "uvicorn[standard]"
```

### Folder Structure

We'll write the FastAPI code in the apps/rest-api folder.

```text
project/
├── apps/
│   └── rest-api/
│       └── run.py    (new file)
```

### run.py

Write the FastAPI router. Using the `Celery` library, create an app with the broker specified. The app's `send_task` method lets you send tasks to the broker.

<div class="file-name">/apps/rest-api/run.py</div>

```python
from random import randint
from fastapi import FastAPI
from fastapi.responses import PlainTextResponse

from celery import Celery

app = FastAPI()

url = "localhost"
username = "guest"
password = "guest"

celery = Celery(
    "Client Publisher App",
    broker=f"pyamqp://{username}:{password}@{url}//",
    backend=f"redis://{url}:6379/0",
)

@app.get("/publish")
def publish_task():
    a = randint(1, 100)
    b = randint(1, 100)

    celery.send_task(
        "tasks.sum.consume_task",
        kwargs={"a": a, "b": b},
        queue="sum-queue",
    )

    return PlainTextResponse(f"FastAPI : {a=},{ b=} Published to the queue")
```

### About send_task

`send_task` is a method that lets you run a Celery task asynchronously without importing it. Because you pass the task's name as a string through the Celery instance, it reduces dependencies between codebases.

- The first argument (=name) specifies the `worker` (=handler function) that will process the task
- The kwargs argument passes arguments to the worker
- The queue argument specifies the broker queue the task goes into

```python
celery.send_task(
    "tasks.sum.consume_task",
    kwargs={"a": a, "b": b},
    queue="sum-queue",
)
```

## Celery Worker

### Folder Structure

Now that tasks are in the broker queue, let's set up an environment to run a **Celery worker** that picks them up and processes them. Create an `apps/worker/` folder and add the files we need.

```text
project/
├── apps/
│   ├── rest-api/
│   └── worker/ 
│       ├── celeryconfig.py (new file)
│       └── run.py          (new file)
```

### run.py

Create a Celery app and update its settings from the `celeryconfig` file with `config_from_object`. Celery's `include` option explicitly registers task modules.

<div class="file-name">/apps/worker/run.py</div>

```python
from celery import Celery

app = Celery(
    "Celery Worker",
    include=[
        "tasks.sum",
    ],
)

app.config_from_object("celeryconfig")
```

### celeryconfig.py

This file holds the configuration: assign a value to each variable. See the [Configuration and defaults](https://docs.celeryq.dev/en/stable/userguide/configuration.html#configuration){:target="_blank"} page.

<div class="file-name">/apps/worker/celeryconfig.py</div>

```python
broker_url = "pyamqp://guest:guest@localhost//"
result_backend = "redis://localhost:6379/0"

task_serializer = "json"
accept_content = ["json"]
result_serializer = "json"
enable_utc = True
timezone = "UTC"
broker_connection_retry_on_startup = True
```

- broker_url: the URL of the message broker
- result_backend: the URL of the backend that stores task results
- task_serializer: the format used to serialize tasks
- accept_content: a list of accepted message formats; here only JSON is allowed
- result_serializer: the format used to serialize results
- enable_utc: enables the UTC time zone
- timezone: sets Celery's default time zone
- broker_connection_retry_on_startup: enables retrying the broker connection on startup

### Adding the Task File

Create a tasks folder and write `sum.py`, the task module that does the actual work.

```text
project/
├── apps/
│   ├── rest-api/
│   └── worker/
│       ├── tasks/
│       │   └── sum.py (new file)
│       ├── celeryconfig.py
│       └── run.py
```

### tasks/sum.py

Celery uses the `@app.task` decorator to define work to be processed asynchronously. A Celery worker pulls tasks defined this way from the queue and runs them. The example below simulates a task that takes a while to finish.

<div class="file-name">tasks/sum.py</div>

```python
import logging
import time

from run import app

@app.task(queue="sum-queue")
def consume_task(a, b):
    time.sleep(5)

    logging.info(f"{a=}, {b=}")
    logging.info(f"Task Done : {a} + {b} = {a + b}")

    return a + b
```

### Running the Worker

When the worker starts, it picks up the tasks already waiting in RabbitMQ's `sum-queue` and processes them. The results are stored in Redis. You can see that even with lots of requests coming in, the four workers work through them one after another!

- `-A run` : specifies the Celery application. Same as `--app`
- `worker` : starts a Celery worker. `beat` is another possible value
- `-Q sum-queue` : the queue(s) the worker consumes. Separate multiple queues with `,`. Same as `--queues`
- `--hostname worker@%h` : the name of the worker. `Worker@Celery Worker`
- `-c 4` : the worker can process up to 4 tasks concurrently. Same as `--concurrency`
- `--loglevel=info` : print info-level logs

```bash
$ cd apps/worker

$ celery -A run worker -Q sum-queue --hostname worker@%h -c 4 --loglevel=info
```

## Wrapping Up

We looked at distributed processing with a task queue using `Celery`. The basic setup is:

- Client: creates tasks and sends them to the queue.
- Broker: stores tasks and hands them to workers.
- Worker: does the actual work.
- Backend: stores task results.

With Celery, you can easily swap `RabbitMQ` or `Redis` for a different broker or backend. It's also worth trying Celery together with other services for distributed processing. 😊
