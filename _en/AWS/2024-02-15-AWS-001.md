Let's look at AWS credentials, and in particular at access keys and AssumeRole.

## AWS Credentials

In AWS, credentials are the security credentials a user or service needs to access AWS resources. AWS uses the following kinds of credentials.

### Password + MFA

- The user name and password used to sign in to the AWS Console
- Multi-factor authentication (MFA) adds a second check through another device, such as an OTP app

![MFA](/assets/img/content/AWS/001/002.webp){:.img-l}

`> MFA for an IAM user`{:.img-caption}

### Key pairs

- A pair of public and private keys used to SSH into Amazon EC2 instances

![EC2 key pair](/assets/img/content/AWS/001/003.webp){:.img-l}

`> EC2 key pair`{:.img-caption}

### Access key

- Access keys are used to access AWS programmatically, e.g. with the AWS CLI or an AWS SDK
- An access key has two parts: an access key ID and a secret access key
- Once created, you can't view the secret again (you have to issue a new key), and you can have at most two keys at a time.

### Temporary Security Tokens

- Tokens that provide temporary security credentials
- Usually issued through the `AssumeRole` API of the AWS Security Token Service (STS)

Among all these credentials, **the ones you'll actually use for development work are mostly access keys and temporary security tokens.**{:.orange}

## Access Keys and Long-Term Credentials

An `Access key` is created from an IAM user and inherits that user's permissions as is. It is a long-term credential: once created, it can be used indefinitely with no expiration. Because it never expires, it's convenient to use.

But a key that never expires tends to be used for a long time, managed carelessly, and eventually becomes a security hole. Here are the classic examples:

1. The key gets committed to git and made public
2. The key you saved when issuing it gets shared with others

When an access key with no expiration leaks like this, whoever has it can exercise every permission of that IAM user.

## Temporary Security Tokens and AssumeRole

Temporary security tokens are tokens with a limited lifetime. Since you can create them dynamically whenever you need them, **they are easier to manage and more secure.**{:.orange}

The way to get a temporary security token is `AssumeRole`, which issues the token through the AWS Security Token Service (STS).

AssumeRole lets you take on a different role. You do the work you need with it, and when you're done you go back to your original permissions.

## Creating a User and Issuing an Access Key

### 1. Create a user

Let's create a user with `Identity and Access Management(IAM)` and issue an access key to use for development. Choose `IAM` - `Users` - `Create user`.

![Switching to a role (console)](/assets/img/content/AWS/001/006.webp){:.img-l}

`> In the IAM service, open the Users menu - Create user`{:.img-caption}

### 2. Add permissions

Choose "Attach policies directly", search for `AmazonEC2FullAccess` and check it. This gives the new user full permissions for EC2. Other services such as S3 remain off limits, because the user has no permissions for them. This is the usual way to operate: grant only the permissions that are needed and manage them.

![Switching to a role (console)](/assets/img/content/AWS/001/007.webp){:.img-l}

`> Add permissions`{:.img-caption}

### 3. Issue an access key

Select the user you created, and you can issue an access key on the `Security credentials` tab. This key carries exactly the same permissions as the user. So it gets the `AmazonEC2FullAccess` permission we gave the user earlier.

![Switching to a role (console)](/assets/img/content/AWS/001/008.webp){:.img-l}

`> Create access key`{:.img-caption}

A screen titled "Access key best practices & alternatives" appears. It doesn't matter much: select `Command Line Interface(CLI)`, check the confirmation at the bottom, move on, and click the **Create access key** button. Your access key is created.

An access key has two values:

- Access key
- Secret access key

The access key ID can be viewed again after it's issued, and it's fine if it becomes public. But **the secret access key must never be made public. An access key has the same permissions as the user it belongs to, so you must take care of it whenever you use it.**{:.yellow} On top of that, an access key is a long-term credential: once leaked, it can be used until you deactivate or delete it, so be especially careful.

The secret access key can't be viewed again after creation, so if you lose it you have to create a new key. Write both values down somewhere private. If needed, download them as a .csv file and keep it safe.

![Switching to a role (console)](/assets/img/content/AWS/001/009.webp){:.img-l}

`> An access key consists of an access key ID and a secret access key.`{:.img-caption}

## Trying the AWS CLI (Command Line Interface)

Now let's use the AWS CLI with the access key we just issued. I'm working on `Ubuntu`; Windows users can download and install it from the [AWS Command Line Interface](https://aws.amazon.com/ko/cli/){:target="_blank"} page. Or I recommend [setting up a WSL development environment](/tool/1){:target="_blank"}.

```bash
$ sudo apt update

$ sudo apt install awscli

$ aws --version
```

Once it's installed, you need to register the access key you issued so you can use AWS services as that user. You can register it with the `aws configure` command. For Default region name, enter the Seoul region `ap-northeast-2`. For Default output format, just press Enter.

```bash
$ aws configure
```

```text
AWS Access Key ID [None] : your access key ID
AWS Secret Access Key [None] : your secret access key
Default region name [None] : ap-northeast-2
Default output format [None] : 
```

With both values set in the AWS CLI, you now have the same permissions as the user you created. Let's check that we can reach EC2. If you get JSON output, the access key is set up correctly in the AWS CLI.

```bash
$ aws ec2 describe-instances
```

```text
{
    "Reservations": [
        {
            "Groups": [],
            "Instances": [
                {
                    ...
```

## Trying AssumeRole

This time, let's give the user we created the `AssumeRole` permission and switch to a different role.

### 1. Give the user the AssumeRole permission

Let's grant the AssumeRole permission to the user. Click the user, and on the Permissions tab choose `Create inline policy`, then search for and select `STS` as the service. Then check Access level - Write - `AssumeRole`. Once the policy is created, you'll see it attached to the user. The user now has the `AssumeRole` permission, which lets it switch to the role it wants.

![Inline policy](/assets/img/content/AWS/001/010.webp){:.img-l}

`> step1. Create an inline policy`{:.img-caption}

![STS](/assets/img/content/AWS/001/011.webp){:.img-l}

`> step2. Select the STS service`{:.img-caption}

![AssumeRole](/assets/img/content/AWS/001/012.webp){:.img-l}

`> step3. Check Write - AssumeRole`{:.img-caption}

### 2. Create the role the user will assume

With the `AssumeRole` permission, you choose which role to switch to and receive the permissions assigned to that role. Here we'll make a role with full S3 access, `AmazonS3FullAccess`, and switch to it. First, let's create the role.

![Create role](/assets/img/content/AWS/001/013.webp){:.img-l}

`> step1. Create a role`{:.img-caption}

Under "Select trusted entity", choose AWS account. Select "This account" and move on. In Add permissions, search for and select `AmazonS3FullAccess`. For the role name, I'll use `dev-assume-role-AmazonS3FullAccess` and create the role.

![Select entity](/assets/img/content/AWS/001/014.webp){:.img-l}

`> step2. Select a trusted entity`{:.img-caption}

Click the role you created and you'll see a value called `ARN`. This value is what lets you switch to the role.

![ARN](/assets/img/content/AWS/001/015.webp){:.img-l}

`> ARN of the created role`{:.img-caption}

### 3. AssumeRole from the AWS CLI

Now let's switch to the role we want from the AWS CLI, using the AssumeRole permission we gave the user. To switch roles, we call the STS `assume-role` API with two options:

- `--role-arn` : the ARN of the target role
- `--role-session-name` : any string

```bash
$ aws sts assume-role --role-arn <ROLE_ARN> --role-session-name <test-session>

$ aws sts assume-role \ 
--role-arn arn:aws:iam::99842...:role/dev-assume-role-AmazonS3FullAccess \
--role-session-name test-session
```

Running AssumeRole gives you two key values plus a token. With those two key values and the token from AssumeRole, you can switch roles.

```text
{
    "Credentials": {
        "AccessKeyId": "ASIA.......",
        "SecretAccessKey": "YwyGY8dF5.......",
        "SessionToken": "IQoJb3JpZ2.......",
        "Expiration": "2024-04-21T08:08:12Z"
    },
    "AssumedRoleUser": {
        "AssumedRoleId": "AROA6Q5UMFQN.......",
        "Arn": "arn:aws:......."
    }
}
```

Let's set temporary environment variables and check with AWS CLI commands whether the role has switched. On Windows, use the `set` command instead of export.

```bash
$ export AWS_ACCESS_KEY_ID=ASIA.......
$ export AWS_SECRET_ACCESS_KEY=YwyGY8dF5.......
$ export AWS_SESSION_TOKEN=IQoJb3JpZ2.......
```

Once you've switched to the role with `AmazonS3FullAccess`, you can access S3, which you couldn't before. Conversely, the role you switched to has no EC2 permissions, so you'll find you can no longer access EC2.

```bash
$ aws s3 ls

$ aws ec2 describe-instances
```

## Switching to a role (console)

On top of that, switching roles in the AWS Console, `Switching to a role (console)`, also runs `AssumeRole` under the hood. Here too, you switch roles by entering the information contained in the ARN: the account (a number) and the role name.

![Switching to a role (console)](/assets/img/content/AWS/001/004.webp){:.img-l}

`> Switching roles in the AWS console`{:.img-caption}

## Wrapping Up

Here's a summary of everything:

1. AWS has several kinds of credentials
2. For development, there are two main kinds
    - Access key: long-term credentials
    - AssumeRole: temporary credentials
3. An `Access key` uses the user's permissions as is, and **since it never expires, a leak is fatal**{:.orange}
4. `AssumeRole` lets you switch to the role you want, and **since it uses tokens that expire, it's far more secure**{:.orange}
