## Prologue

I recently joined a study group, and it fell apart. Hmm... looking back on my own study group experiences, the ones built around assigned presentations mostly didn't go well. I'd prepare hard for the day I was presenting, but it wasn't easy to stay focused when it wasn't my turn. 🙄

I think the key to a successful study group is **active communication between members**. So, since I was starting a new coding test study group anyway, I decided to build an environment where members could give each other feedback.

## What kind of environment to build

First of all, solving problems on a coding test site is the best way to go. Studying in the same environment as a real hiring test is ideal, after all.

But for the problems you just can't crack, I thought it would be nice to have an environment where you can add tests and run them. On top of that, the goal isn't solo study; it's to get the study group members involved.

So the core of the environment I had in mind came down to this:

1. An environment where you can add tests and debug easily locally → **pytest**
2. An environment for feedback and motivation between members → **github Actions**

## The local pytest environment

First, I set up an environment for testing locally with `pytest`. I say "locally," but since it's a space shared with other members, it needed a few rules.

1. It's shared, but each person needs their own space → GitHub ID
2. A test environment that uses the same tests but can dynamically run the code I choose
     → `pytest_addoption`, `import_module`

## Ground rules for the test environment

To make the tests run in GitHub Actions too, I needed some way to tell people apart. So I built the test environment on the premise that each person's GitHub ID is the name of their own space.

Since the study group follows a book, I first had problems organized into folders and files by chapter.

1. In the `src/your-id/ch_number` folder, write the solution files and functions following the rules.
2. In the `tests/ch_number` folder, write the code that tests the solution functions. 
3. The tests use the dynamically provided ID to call the target person's function.

## Overall project structure

```text
src
└─ your-id
   └─ ch_01
      └─ solution_01.py :: soultion()
      └─ solution_02.py :: soultion()
   └─ ch_02
   
tests
└─ ch_01
   └─ test_01.py :: test()
   └─ test_02.py :: test()
└─ ch_02
   └─ ...
   └─ ...
└─ conftest.py
└─ .env
pytest.ini
```

## pytest: accepting dynamic input

The important point in the rules above is that each person's test targets live under their own ID. So first, I use `pytest_addoption`, which lets `pytest` accept user options when it runs, to create a custom option that takes the ID. 

<div class="file-name">tests/conftest.py</div>
```python
import pytest
from dotenv import load_dotenv

def pytest_addoption(parser):
    # read the .env file from the current working directory
    load_dotenv()

    # read environment variables
    USER_ID = os.getenv("USER_ID")

    parser.addoption(
        "--id",
        action="store",
        default=USER_ID,
        help="Don't edit this! Use .tests/.env instead!",
    )
```

### Running pytest directly

With the custom command-line option added, you can pass the value in when you run `pytest`.

```bash
$ pytest --id=your-id
```

### Running or debugging in VScode

I also set a default value for when you run it with the debugger from VScode's Run and Debug view. Here, I used **`load_dotenv()`** to load the **`.env`** file and passed it to `parser.addoption()` as the default. Setting the `--id` value in `.vscode/launch.json` works too.

```text
# src/tests/.env

USER_ID=tiaz0128
```

## A function that finds the path when a test runs

Now let's create a `pytest.fixture` that can load files dynamically. **We need the path at the moment the actual test file runs**, because the test file's path is what we use to find the actual target to test. 

I'll make a `fixture` for the function that, when a test file runs, works out the path of the matching solution function. I'll also turn the provided user ID into a `fixture`.

<div class="file-name">tests/conftest.py</div>
```python
# existing pytest_addoption code...

def get_test_file_path(file_path, user_id):
    script_path = os.path.abspath(file_path)

    # parent folder name
    parent_path = os.path.dirname(script_path)
    parent_directory = os.path.split(parent_path)[-1]

    # extract the number from the file name
    file_name = os.path.basename(file_path)
    numbers = re.findall(r"\d+", file_name)[-1]

    return f"src.{user_id}.{parent_directory}.solution_{numbers}"
@pytest.fixture(name="user_id")
def setup(request):
    user_id = request.config.getoption("--id")
    return user_id
@pytest.fixture(name="func")
def setup_lib():
    return get_test_file_path
```

## importlib.import_module(): importing the test target dynamically

In each test file, we use `get_test_file_path`, the function we just made that works out the current path. The reason for doing it per file is to use `__file__`, **a file attribute that is set automatically** when each file runs. 

1. Take `__file__`, which holds the path of the currently running test file, as the argument
2. Call `get_test_file_path`, received through a `fixture`.
3. That function gives the path to the target function matching the current test file.
4. Finally, the module at that path is imported dynamically at runtime with `importlib.import_module`.

<div class="file-name">tests/ch_01/test_01.py</div>
```python
@pytest.fixture(name="module")
def setup_module(user_id, func):
    path = func(__file__, user_id)

    return importlib.import_module(path)

@pytest.fixture(
    name="test_input",
    params=[
        ([1, -5, 2, 4, 3], [-5, 1, 2, 3, 4]),
        ([2, 1, 1, 3, 2, 5, 4], [1, 1, 2, 2, 3, 4, 5]),
        ([1, 6, 7], [1, 6, 7]),
    ],
)
def setup(request):
    return request.param

@pytest.mark.ch_01
def test(module, test_input):
    # given
    *args, excepted = test_input

    # when
    result = module.solution(*args)

    # then
    assert result == excepted
```

## Picking which tests to run

With `pytest` options and markers, you can easily test all sorts of scenarios. The basic folder layout holds test files by chapter, and every test file in a chapter is tagged with a `pytest.mark.ch_XX` marker. And since each test file is named `test_number` after its unique problem number, you can also run just a single test.

```bash
# test by chapter
$ pytest -m ch_01

# a specific test only 
$ pytest -k 'test_01'
```
