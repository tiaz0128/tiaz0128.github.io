## Factory

![factory](/assets/img/content/python/006/001.webp){:.img-s}

The factory pattern is one of the design patterns for creating objects. Its main purpose is to **separate object creation logic from client code**.

So let's imagine we're running a pizza shop and learn about the factory pattern!

## step 1. Let's open a shop that sells only cheese pizza

### The situation

We've opened a shop that makes only cheese pizza. Every order is the same kind, so all we have to make is _'cheese pizza'_.

![Cheese pizza shop](/assets/img/content/python/006/002.webp){:.img-s}

### Code

There's only one kind of pizza on order, so no need to think: we just make cheese pizza.

```python
from enum import StrEnum

class PizzaType(StrEnum):
    CHEESE = 'cheese pizza'
```

```python
class PizzStore:
    def order(self, pizza_type: PizzaType) -> Pizza:
        pizza = CheesePizza()
        return pizza
```

### Class diagram

We end up with a composition structure in which the `CheesePizza` object lives inside `PizzaStore`. Composition basically creates a tight coupling between objects. Still, hmm... at this scale it doesn't look like much of a problem.

## step 2. Let's add more kinds of pizza!

### The situation

Business is booming, so we happily expanded the menu with all kinds of pizza.

> "Why does business keep going so well?!"

![Business is booming](/assets/img/content/python/006/003.webp){:.img-s}

Now we have to make many different kinds of pizza depending on the orders coming in. The more kinds of pizza there are, the harder it gets. With so many items on the menu, it looks like we'll have to drop the ones that don't sell well, too.

### Code

Now we have to make each pizza according to the kind ordered, so we add branching. But every time we add a kind of pizza, we need more and more branches.

```python
from enum import StrEnum

class PizzaType(StrEnum):
    CHEESE = 'cheese pizza'
    CLAM = 'clam pizza' # added
    HAM = 'ham pizza'   # added
```

```python
class PizzStore:
    def order(self, pizza_type: PizzaType) -> Pizza:
        match pizza_type:
            case pizza_type.CHEESE:
                pizza = CheesePizza()
            case pizza_type.CLAM:
                pizza = ClamPizza()
            case pizza_type.HAM:
                pizza = HamPizza()
            #
            # more and more branches...
            #

        return pizza
```

### Class diagram

There's another problem just as serious as the tangled branching: the client object, `PizzaStore`, becomes tightly coupled to an ever-growing number of `Pizza` classes.

## step 3. Let's get our pizzas from a factory

### The situation

We decide to stop making all those kinds of pizza ourselves. Instead, we'll sell pizzas made at a factory. With the pizzas coming from the factory, the shop, once cluttered from making so many kinds of pizza, is now neat and tidy!

![Pizza factory](/assets/img/content/python/006/004.webp){:.img-s}

### Code

Trying to make many kinds of pizza made the pizza shop class complicated. Let's change it to get pizzas from a factory object that does nothing but make pizza. The client object no longer depends on all the different pizzas.

```python
from enum import StrEnum

class PizzaType(StrEnum):
    CHEESE = 'cheese pizza'
    CLAM = 'clam pizza'
    HAM = 'ham pizza'
```

```python
class PizzStore:
    def __init__(self):
        self.factory = PizzaFactory()

    def order(self, pizza_type: PizzaType) -> Pizza:
        pizza = self.factory.make_pizza(pizza_type) # a tidier shop
        return pizza
```

```python
class PizzFactory:
    def make_pizza(self, pizza_type: PizzaType):
        match pizza_type:
            case pizza_type.CHEESE:
                pizza = CheesePizza()
            case pizza_type.CLAM:
                pizza = ClamPizza()
            case pizza_type.HAM:
                pizza = HamPizza()

        return pizza
```

## So what's the benefit?

When you write a factory class, you might think:

> Didn't we just push the complicated problem onto another object?

It can certainly look that way. That may be because, so far, we've only considered a single object using the factory. Let's think bigger. What if many other objects use the factory object?

### Code

Thanks to the factory, there's no trace of any pizza in either `PizzStore` or `PizzFoodTruck`.

```python
class PizzFactory:
    def make_pizza(self, pizza_type: PizzaType):
        match pizza_type:
            case pizza_type.CHEESE:
                pizza = CheesePizza()
            case pizza_type.CLAM:
                pizza = ClamPizza()
            case pizza_type.HAM:
                pizza = HamPizza()

            # menu items sold only at the food truck
            case pizza_type.MINI_CHEESE:
                pizza = MiniHamPizza()
            case pizza_type.MINI_CLAM:
                pizza = MiniHamPizza()
            case pizza_type.MINI_HAM:
                pizza = MiniHamPizza()

        return pizza
```

```python
class PizzStore:
    def __init__(self):
        self.factory = PizzaFactory()

    def order(self, pizza_type: PizzaType):
        pizza = self.factory.make_pizza(pizza_type) # at the shop
        return Pizza
```

```python
class PizzFoodTruck:
    def __init__(self):
        self.factory = PizzaFactory()

    def order(self, pizza_type: PizzaType):
        pizza = self.factory.make_pizza(pizza_type) # and at the food truck 
        return Pizza
```

### Class diagram: SimpleFactory

This is how the factory pattern removes the dependency on the pizzas themselves. All those pizza objects that are complicated to create are now handled through a single factory object!

## Types of factory patterns

There are several kinds of factory patterns. The one we just saw is the most basic structure, called the `SimpleFactory` pattern. Three patterns are commonly discussed:

1. `SimpleFactory`
2. `MethodFactory`
3. `AbstractFactory`

## Wrapping up

The factory pattern is all about separating the logic that creates other objects. Separating object creation logic brings these main benefits:

1. It removes the client object's complex dependencies on creating other objects
2. Other client objects can reuse the same factory
3. It reduces the number of places you have to maintain
